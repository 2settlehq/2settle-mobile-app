# 2Settle Play Store readiness audit (v2 — independent re-audit)

Audit date: September 15, 2026. This supersedes the September 14–15, 2026 audit below the `---` divider at the end of this file, which is retained for traceability but should not be treated as current.

**Methodology:** This audit was produced by reading the current source directly — four independent reviewers covered Android build/signing, app-side auth/session/storage, app-side account-deletion/legal-pages/unfinished-features, and the `mobile-api` gateway, none of which consulted the prior report while forming conclusions. Every finding below cites a specific file:line read this session. Current Google Play policy requirements were confirmed via live web search on September 15, 2026, not from training-data knowledge. This is a source/configuration review, not a penetration test, not a signed-build inspection, and not a legal compliance certification. No app code was changed, no signed release was built, no live money moved, and no Play Console was accessed.

**Scope limitation:** The `payment-engine/backend` repo that the prior audit examined (OTP hashing, refresh-token rotation, HMAC config, IP allowlisting, database locking, watcher services) is **not present in this checkout** and could not be re-verified. Everything below about the backend is limited to what `mobile-api` (the gateway) shows; treat any payment-engine-internals claims in the superseded report as unverified, not re-confirmed.

**Assessment: not ready for production submission.** The picture is more specific and in some places more alarming than the prior audit — and also better in a few places, where the gateway has clearly been hardened since the last check.

## Important framing correction

This is very likely an **update to an already-live Play Store app**, not a new submission. Evidence: `README.md` states publishing "under the existing Play Store app identity requires the existing release/upload signing credentials," and the app's splash screen hardcodes a version label `2Settle V2.36.38` (`lib/pages/splash_screen/splash_screen_widget.dart:28`) implying many real prior releases — while `pubspec.yaml:18` currently says `version: 1.0.0+1`. Treat "choose your package ID" and "set up your developer account" guidance below as **confirm what's already live**, not greenfield decisions.

### Reconciled finding: gift creation is calling an authenticated gateway route with no auth header

Two independent reviewers found opposite halves of the same problem, and I verified both directly this session:

- **App side** (`lib/pages/create_gift/create_gift_widget.dart:245-265`): posts to `ApiConfig.paymentsUrl` with only `{'accept': 'application/json', 'content-type': 'application/json'}` — **no `Authorization` header** — and sends `payer: {chatId, phone}` sourced from `MobileIdentityService` (a client-generated identifier, not a verified session).
- **Gateway side** (`mobile-api/api/payments/index.js:22-28`, confirmed by the gateway auditor this session): the payment-creation route now **requires and verifies a bearer token** via `verifyEndUser`, and derives payer identity *exclusively* from that verified token — client-supplied payer fields in the body are explicitly ignored.
- `ApiConfig.paymentsUrl` (`lib/config/api_config.dart:28`) resolves to `$baseUrl/api/payments`, i.e. exactly the gateway route just described — confirmed by reading both files together.

**This means the gift-creation call as currently coded will be rejected (401) by the gateway's current code**, unless the deployed gateway on Vercel is running older code than this checkout. This is good news for security (the gateway won't accept a forged identity) but is very likely a **functional break in a core money-movement feature** that needs to be reproduced against the real deployed environment before anything else here matters. The same missing-Authorization-header pattern also applies to gift cancellation (`lib/pages/gift_claim_details/gift_claim_details_widget.dart:220-225`) and bank validation (`lib/pages/pay_page/pay_page_widget.dart:481-488`) — check each against its corresponding gateway route the same way.

## What's actually fine (verified, not assumed)

- **Android manifest permissions are minimal and justified**: only `INTERNET` and `POST_NOTIFICATIONS` — no SMS, contacts, storage, or location permissions anywhere in main/debug/profile manifests.
- **No secrets committed anywhere**, in either repo, ever — checked via full `git log --all -p` on `key.properties` and `.env*` patterns, plus broad key-literal greps. `.gitignore` correctly excludes both.
- **`FileProvider` is correctly non-exported**, and no cleartext-traffic weakening or custom network security config exists — default HTTPS-only behavior applies.
- **`compileSdkVersion`/`targetSdkVersion` are already 36**, which already satisfies Google Play's Aug 31, 2026 target-API requirement (confirmed against current policy, see below) — this is done, no action needed.
- **No ABI/native-library red flags** for the 16 KB page-size requirement (no custom `abiFilters`/`packagingOptions`, NDK r28 defaults to 16 KB-aligned output) — not independently verified by an actual build/zipalign check, but no evidence of a problem either.
- **`AuthService.logout()` and `verifyEndUser`/`callerOwnsReference` on the gateway are both correctly implemented** where they're actually invoked — payment creation and cancellation now derive payer identity exclusively from a server-verified token rather than trusting the client, a real fix since the prior backend audit (see corrections below).
- **Gateway HMAC secrets never leave the server** — `process.env` only, never logged (zero `console.*` calls in `mobile-api/api` or `mobile-api/lib`), never returned in a response body.
- **Settings → Edit Profile / Account / Security / Notifications, Account → Bank & beneficiary / Receive payment details, and Security → Change app passcode are all real, working destinations**, not stubs.
- Firebase web API key hardcoded in `lib/backend/firebase/firebase_config.dart:8` is a **false-positive concern** — it's a standard public client identifier, not a secret; flagged only so a reviewer doesn't mistake it for a leak.

## Corrections to the superseded (Sept 14–15) audit

- **Gift/payment authorization is more nuanced than "no bearer token, might be intentional."** The gateway now actively verifies and enforces identity server-side for payment creation and cancellation — but the *app's* current call to gift creation doesn't send the token the gateway now requires (see reconciled finding above). The old framing ("certain gift routes may intentionally be public") is no longer accurate for payment creation; it's likely a broken integration, not an intentional public route.
- **Cancellation ownership checking, which the original backend audit's AUDIT.md flagged as missing, is now implemented** (`callerOwnsReference`, wired into both cancel and payment-status lookup). The gap has moved to gift **claim confirmation**, which the old audits didn't check.
- **`authRefreshUrl` "configured but no use found" is confirmed again independently** — still true, still unused.
- **The 16 KB page-size requirement is no longer a "consult the deadline" future item.** The deadline for *existing app updates* was **May 1, 2026** — already past as of this audit date (Sept 15, 2026). Treat this as a currently-binding requirement, not upcoming.
- **The package-ID question ("deliberately choose the permanent package ID") undersold how resolved this already looks.** `google-services.json` already has Firebase client config for the `.original`-suffixed ID, meaning this was very likely already decided and shipped — the risk now is *accidentally changing it*, not failing to choose it.
- **The prior legal-pages finding checked the wrong domain.** The app actually links to `spend.2settle.io/privacy` and `/terms`, not a bare `2settle.io`/`.io` path — re-verify liveness against the correct URLs.
- **This is very likely an app *update*, not a new submission** — the prior audit's Play Console guidance (organization account setup, D-U-N-S, choosing a package ID) should be read as "confirm what's already registered," not "decide from scratch."

## Google Play launch criteria — confirmed current as of September 15, 2026

(Verified via live search this session, not recalled from training data.)

- **Target API level:** as of **August 31, 2026**, new apps and app updates must target **Android 16 (API level 36)** to be submittable at all (extension requests to Nov 1, 2026 are available if needed). This app already targets 36 — compliant, no action needed.
- **16 KB page size:** new apps/builds had to support it from **Nov 1, 2025**; **all updates to existing apps** had to support it from **May 1, 2026** — this deadline has already passed. Verify with an actual build, not just config inspection.
- **Account deletion:** required for any app that supports account creation — both an **in-app** deletion flow and a **public web URL**, declared in the Data Safety form. This app currently has neither (blocker #9 above).
- **Data Safety form:** required for every app, with data practices matching the hosted privacy policy exactly; mismatches are a common rejection/removal trigger. April 2025 policy tightened classification of device identifiers (e.g. Android ID) — worth a fresh inventory pass, not just reusing an old declaration.
- **Financial Features Declaration:** required for any app with crypto/payment/wallet features (this app charges via crypto per `create_gift_widget.dart:235`). For EU distribution, full **CASP authorization** is now generally required (France's national DASP registration transition allowance only runs through **June 30, 2026**) — confirm this with whoever owns compliance/licensing before EU launch countries are selected.
- **Closed-testing gate (12 testers / 14 continuous days)** applies only to **personal** Play Console accounts created after **Nov 13, 2023**; organization accounts are exempt from this specific gate but should still go through internal/closed testing as good practice.
